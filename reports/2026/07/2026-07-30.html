ONNX · Cross-Platform ONNX Runtime on iOS: Deploy One Model Across iPhone and Android via Core ML Execution Provider

If your team ships AI features on both iOS and Android, maintaining separate model formats is expensive. The ONNX Runtime + Core ML Execution Provider pattern lets you train once, export to ONNX, and run on both platforms — with the iOS path routing directly through the Neural Engine. Here's the practical workflow: (1) Train in PyTorch/TensorFlow, export to .onnx format using standard ONNX export tools. (2) On iOS, use ONNX Runtime's CoreML EP: let session = try ORTSession(env: env, modelPath: path, sessionOptions: options) where options enable the Core ML provider. The runtime automatically routes compatible ops to the ANE. (3) The critical gotcha — operator coverage: if your model uses an op unsupported by the CoreML EP, it silently falls back to CPU — destroying your latency budget. Before shipping, run onnxruntime_profile to verify 100% of ops hit the ANE. Common offenders: custom attention patterns, GroupNorm, and certain reshape operations. Replace them with ANE-friendly equivalents. (4) Performance vs. native Core ML: expect 10-15% overhead vs. a hand-optimized .mlpackage. For most features, the cross-platform convenience outweighs this gap. Reserve native Core ML for your app's hottest inference path (e.g., real-time camera pipeline). (5) For Binance iOS: your fraud detection or price anomaly models likely already exist in PyTorch for the backend — with ONNX, the same model runs on-device for zero-latency client-side pre-screening before server confirmation. Quantization · 4-bit Models 4-bit Quantization for Mobile: Run 3B Parameter Models in Under 2GB RAM on iPhone

The single most impactful optimization for on-device LLMs: 4-bit quantization — reducing model weights from 16-bit floats to 4-bit integers with minimal quality loss. A 3B parameter model drops from 6GB (FP16) to ~1.5GB (INT4), making it feasible on any iPhone 15+ device. Here's your implementation guide: (1) Choose your quantization method: GPTQ (best quality, requires calibration data) or AWQ (activation-aware, better for decoder models). For MLX Swift models, Apple's built-in quantizer handles this: mlx_lm.convert --model meta-llama/Llama-3.2-3B --quantize --q-bits 4. (2) Quality validation: run your eval suite on both FP16 and INT4 versions. Expect <5% degradation on text generation, <2% on classification tasks. If degradation exceeds 8%, try mixed quantization — keep attention layers at 8-bit while compressing feed-forward layers to 4-bit. (3) Memory management on iOS: declare your model's memory budget in Info.plist using the new iOS 27 CoreAIMemoryBudget key. The OS pre-allocates memory during launch, preventing OOM during inference. (4) The latency trick — weight preloading: mmap the quantized weights file on app launch but don't decompress until first inference request. The file stays in the page cache between app uses, making subsequent launches near-instant. (5) For real-time features: 4-bit models on A18+ chips deliver 25-35 tokens/sec — fast enough for streaming text generation that feels instant to users. Combine with speculative decoding (draft with tiny model, verify with main model) for another 40% throughput boost. MLX Quantization Examples →

Instruments · ANE Profiling Xcode 18 Core AI Instrument: Find and Fix Neural Engine Pipeline Stalls

Running a model "on the Neural Engine" doesn't mean it's running efficiently on the Neural Engine. Xcode 18's Core AI Instrument reveals exactly where your inference pipeline stalls — and the fix is usually a single operator replacement. The profiling workflow: (1) Attach the Core AI template: in Instruments, select the new "Core AI" profiling template. Run your app and trigger inference. You'll see a flame graph showing each layer's execution: green = ANE, blue = GPU, red = CPU. Any red layer is a pipeline break. (2) Identify the #1 stall pattern: a single unsupported op forces the entire subsequent pipeline off the ANE. The most common culprits in 2026: LayerNorm with non-standard epsilon, GatherND with dynamic indices, and custom GELU implementations. Replace with ANE-friendly equivalents during model conversion. (3) Memory transfer overhead: the instrument shows data copies between compute units. Each ANE→GPU→ANE transition costs 0.5-2ms. If your model ping-pongs between units, consolidate by restructuring layers or using MLComputeUnits.cpuAndNeuralEngine to avoid GPU involvement entirely. (4) Batch size optimization: the ANE handles batch=1 differently from batch=4+. Profile both — for non-interactive workloads (processing notifications in background), batch=4 often gives 3x throughput at only 1.5x latency. (5) The "golden path" checklist: Conv2D, MatMul, Softmax, standard GELU, LayerNorm (standard), Reshape (static shapes) = full ANE execution. Anything outside this set needs verification.
