RAG · On-Device Local-First RAG on iOS: MLX Embeddings + Core AI Generation for Private Retrieval

Retrieval-Augmented Generation (RAG) is the highest-ROI pattern for grounding LLM output in your app's real data — and on iOS you can now run the entire pipeline on-device for zero-latency, zero-data-leak retrieval. The architecture: (1) Embed at index time: chunk your knowledge base (FAQs, product docs, support articles) into ~512-token windows, run each through an MLX-optimized embedding model (e.g. bge-small-en quantized to 4-bit, ~120MB) and store vectors in a local SQLite table with a VECTOR column. (2) Retrieve at query time: embed the user query with the same model, run cosine similarity against the top-K (K=5) chunks — this is pure CPU work, ~5ms for 10k vectors. (3) Generate with Core AI: feed the retrieved chunks as context to your on-device generation model: let response = try await generator.predict(prompt: buildPrompt(query, chunks)). (4) The critical quality lever — chunk overlap & metadata: 15% overlap between chunks prevents context splits; tag each chunk with a source_id so you can cite provenance in the UI ("Based on: Help Center › Withdrawals"). Users trust grounded answers 3x more when the source is shown. (5) For Binance iOS: a local RAG over the Help Center + API docs lets users ask "how do I enable withdrawal address whitelisting?" and get an instant, private, cited answer — no server round-trip, works offline. Re-index nightly via a background BGProcessingTask. MLX Examples →

Tool Use · Function Calling Designing a Reliable Tool Interface: Schema Discipline, Validation & Graceful Failure

Most agent failures in production trace back to one root cause: sloppy tool interfaces. The model isn't broken — your tool contract is. The fix is a disciplined schema-first approach: (1) Define tools as strict JSON Schema with required fields, enum constraints, and description on EVERY parameter (the description is what the model actually reads to decide when/how to call). A vague "amount": number fails; "amount": number, "description": "USD value, must be > 0 and < user balance" succeeds. (2) Validate before execution: never trust model output directly. Run every tool call through a validator (Codable decoding in Swift) and return a structured error — not a crash — on mismatch: {"error": "amount exceeds balance", "suggestion": "call get_balance first"}. The model reads the error and self-corrects. (3) Idempotency keys: every mutating tool (transfer, submit order) must accept an idempotency_key. If the agent retries a duplicate call (common after a timeout), the key prevents double-execution. This single pattern eliminates the most dangerous class of agent bugs. (4) Timeout + fallback: wrap every tool call in a 10s timeout; on expiry return {"error": "timeout", "retry_after_ms": 2000} rather than blocking the agent loop. (5) Observability: log every tool call (name, args, result, latency) to a structured store — you cannot debug an agent you cannot see. Anthropic Tool Use Guide →

Agent Arch · Guardian Gates Agent Orchestration with Guardian Gates: Checkpointed Multi-Step Workflows That Don't Run Away

Autonomous multi-step agents are powerful — and dangerous. The pattern that keeps them safe in production: Guardian Gates — explicit checkpoints where a cheap verifier model (or rule) approves, modifies, or halts the agent's plan before irreversible actions. The orchestration pattern: (1) Plan → Gate → Execute → Gate → Verify: the main agent produces a step plan; a Guardian (a fast, cheap model like Haiku/Luna with a strict rubric) reviews the plan against your policy ("does this touch prod data? does it spend money? does it modify shared state?"). Only approved steps execute. (2) Classify actions by blast radius: Tier 0 (read-only, auto-approve), Tier 1 (local file write, auto-approve with logging), Tier 2 (network call / API mutation, require Guardian approval), Tier 3 (production deploy / financial transaction, require human approval). Hard-code the tier mapping — never let the agent self-classify. (3) State machine, not free-form loop: implement the agent as a finite state machine (Planning → GateReview → Executing → ResultCheck → Done) with explicit transitions, not a while-loop that "calls itself." This bounds runtime and makes failure modes debuggable. (4) Budget enforcement: track cumulative cost/tokens per run; hard-stop at a threshold (e.g. $2 or 50 tool calls). Agents that exceed budgets almost always indicate a loop bug. (5) For iOS/Binance: any agent that touches trading, withdrawals, or account settings must route Tier 3 actions through a human confirmation sheet in the UI — the agent prepares, the user approves with biometrics. Automation up to the point of irreversibility; human at the trigger. Anthropic Agent Patterns →
