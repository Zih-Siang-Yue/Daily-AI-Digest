Spec-Driven · Skills Adopt GitHub Spec Kit as the Reviewed Front-Door for Any Agent-Authored iOS Change

GitHub's Spec Kit (open-source, now 120K+ stars, 30+ agent support) operationalizes the spec-as-source pattern (Aug 14's tip) as a concrete specify CLI workflow: constitution.md (non-negotiables) → spec.md (what & why) → plan.md (architecture) → tasks.md (atomic agent tasks) → /speckit.implement. For a Binance iOS team, the move is to wire this as the mandatory front-door for any Cursor/Claude Code change that touches more than N files: no spec, no agent run. The discipline kills two failure modes at once — (1) it bounds blast radius (the agent can only implement what tasks.md lists), and (2) it makes review tractable (a human reviews the spec once, not 40 generated diffs). Spec-Driven · Maturation

"Vibe Coding" Meets Its Structured Counter-Movement — Spec-Driven Development Gains Traction

A visible maturation is underway in AI-assisted development: the pure "vibe coding" approach (natural-language, high-level prompts, rapid prototyping) is being supplemented — not replaced — by spec-driven development (SDD), where a detailed machine-readable spec is authored before the agent writes code. The catalysts: GitHub's Spec Kit (120K+ stars), the "review fatigue" naming (Aug 16), and growing concern over reliability/security gaps in unconstrained vibe-driven output. The emerging consensus is a hybrid — vibe for exploration and prototyping, SDD for anything shipping to production. Why it matters: (1) for a Binance iOS team, the practical split is clear: vibe-code the prototype, then re-author as a spec before the agent touches the production codebase — the spec becomes the review surface, not the generated diff; (2) it reframes the agent procurement question: the differentiator is no longer "which agent vibes best" but "which agent best supports the spec→plan→tasks→implement loop"; (3) expect SDD to absorb the AgentSecOps pattern (Aug 12) — the constitution.md is where the security non-negotiables live, enforced before code exists. A concept materializing in the FATF's recent DeFi report: the "control or sufficient influence" (COSI) test — a framework for determining whether a DeFi protocol should be subject to AML/CFT regulation based on whether any party exerts practical control over it, rather than formal ownership.
