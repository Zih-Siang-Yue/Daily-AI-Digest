Edge AI · Apple Neural Engine Pin Your Core ML Model to the Apple Neural Engine — and Quantize Before You Ship

The Apple Neural Engine (ANE) delivers the best perf-per-watt for supported models, yet most teams leave 3–5× latency on the table by letting Core ML silently fall back to CPU/GPU. The fix has two parts: (1) set MLModelConfiguration().computeUnits = .all so Core ML routes ANE-friendly subgraphs onto the Neural Engine, and (2) quantize to int8 / 4-bit palettization with coremltools before conversion — the ANE strongly prefers low-precision weights and a constrained op set. Verify routing in the Core ML Instrument's "ANE subgraph" view; if your subgraph stays on CPU/GPU, the culprit is almost always an unsupported activation or custom layer (swap to an ANE-supported one). coremltools optimize →

Edge AI · ONNX Mobile Reuse One Model Across iOS & Android With ONNX Runtime Mobile's Core ML Execution Provider

Maintaining parallel Core ML (.mlpackage) and TFLite/NNAPI pipelines per platform is the silent tax of on-device ML. ONNX Runtime Mobile ships a Core ML Execution Provider that delegates supported ops to Core ML — which in turn can land on the ANE — so you export one ONNX model and run it natively on iOS (via Core ML/ANE) and Android (via NNAPI/GPU). Wire it as ort.InferenceSession(..., providers=['CoreMLExecutionProvider']) on iOS builds, falling back to the CPU EP for ops Core ML rejects. The payoff: a single model artifact, a single test surface, and ANE acceleration where supported — instead of two divergent on-device stacks. ONNX RT Core ML EP →
