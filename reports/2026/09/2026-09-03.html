💡 Daily Tech Tips — Thursday: Edge AI & On-Device ML (Neural Engine, MLX, ONNX)
Core AI · Neural Engine Verify Ops Actually Land on the Neural Engine — Don't Let Them Silently Fall Back to CPU

An on-device model only hits its latency/battery budget if its compute-heavy ops dispatch to the Apple Neural Engine (ANE) — but ops quietly fall back to CPU/GPU when a layer isn't ANE-supported, and your profiler won't shout about it. The deployable check: in coremltools, target ComputeUnit.GPU_AND_NEURAL_ENGINE, then open the Core AI Debugger's op-level view (cf. Aug 29) and confirm each op's assigned compute unit — flag any op on CPU as a conversion rework. It matters more in 2026 because the silicon budget just grew: the M6 chip's dual 16-core Neural Engine doubles peak AI compute, and the A20 Pro (2nm, TSMC-exclusive) raises sustained on-device headroom — but only code that actually dispatches to the ANE cashes that dividend. MLX · Quantization Quantize to int4/int8 — the Gate Between "Runs on My Mac" and "Ships on an iPhone"

On-device LLM deployment is gated by memory, not just speed: a 3B-parameter model at fp16 is ~6GB (uncomfortable on a mid-range iPhone with the app's own footprint); at int4 it's ~1.5GB (ships). The loop: quantize on your Mac with mlx_lm.convert (4-bit/8-bit), sanity-check quality on a held-out eval set (cf. Aug 22's eval gate), then convert the quantized weights to a .mlpackage and serve through Core AI (cf. Sep 1's MLX-LoRA→Core-AI path, now extended to the inference/compression step). For a Binance iOS feature — an on-device transaction-narration or support-triage LLM — int4 quantization is what turns a Mac demo into a ship-grade iPhone model; ship the int4 build, keep the fp16 build for debug. MLX examples →

Hybrid · Routing On-Device-First With a Cloud Fallback — Route Only When the Local Model Is Out of Its Depth

Apple's own 2026 trajectory is hybrid: Core AI/Foundation Models run the bulk on-device (zero token cost, zero egress — Aug 29's ZDR-tier default), while reasoning-heavy/long-context work escalates to a cloud model. Mirror that as a routing rule in your own app: classify the query on-device, serve locally unless it crosses a confidence or context-length threshold, and only then escalate to a cloud model through a model-router (cf. Aug 31's load-bearing router abstraction). For a Binance iOS feature, this is the cost/privacy frontier — most user queries (a balance lookup, a transaction classify) never leave the device; only the hard ones cost a token. Pin the routing threshold to your eval scores, not a guess, so the fallback fires on measured weakness. On-device sovereignty →

Claude Code · Security

Claude Code Stores OAuth Tokens in Plaintext on Linux/Windows — Despite "Stored Securely" Docs

A verified technical finding (Sep 2, secretspec.dev): Claude Code 2.1.257 stores MCP OAuth access tokens in plaintext at ~/.claude/.credentials.json (mode 0600) on Linux and Windows, despite documentation claiming tokens are "stored securely"; macOS uses the encrypted Keychain (falling back to plaintext only if unavailable). Notably, OpenAI's Codex already makes MCP OAuth storage configurable (auto/file/keyring backends) — a precedent for a fix. Why it matters: this extends Aug 31's "agent session as attack surface" thread — the session tokens that let an agent act on your behalf are stealable-and-replayable bearer credentials sitting in a plaintext file on dev machines. How to use it: on Linux/Windows, treat ~/.claude/.credentials.json as a production secret — restrict file perms, run Claude Code under a dedicated OS user, rotate MCP OAuth tokens, and watch for a keyring-backed credential store. (Caveat: the author is affiliated with SecretSpec and advocates for its SDK, but the plaintext-storage finding stands on direct inspection.) Source →

Agentic Coding · Discourse "Are Coding Agents Too Cautious Because They Estimate Work in Human Time?"

A resonant Ask-HN thread (Sep 2) names a friction every agent user hits: a model calls a task "several days of work," then finishes it in 20–30 minutes in auto mode — and worse, once it decides a task is large, it starts reducing scope, splitting, or avoiding critical parts that add real value. The diagnosis: agents import human-time heuristics that understate their own throughput, then self-curtail against a budget that doesn't apply to them. Why it matters: this is the scope-estimation sibling of Sep 1's "harness engineering" — the binding skill isn't a better prompt, it's overriding the agent's false human-time priors so it doesn't silently drop your highest-value work. How to use it: when prompting, give an explicit scope floor ("do not split or reduce; attempt the full implementation") and estimate in agent-steps, not human-hours; treat a model's "this is large" as a flag to scope-up the instruction, not scope-down the task. Architecture "Context Engineering" — The Context Layer Becomes a Managed Discipline, Beyond Prompt Engineering

A concept surfacing in the 2026 architecture discourse: as agents act across long horizons, the binding skill shifts from crafting a single prompt to engineering the context window — retrieval, compression, memory management, and tool-result curation as a managed architectural layer, not an afterthought. It's distinct from Sep 1's "harness engineering": the harness is the control loop (hooks, permissions, abort paths); context engineering is the content of what the model sees. Why it matters NOW: (1) for on-device iOS AI — where a 3B model's context budget is tiny (cf. today's int4-quantization tip) — context engineering isn't optional; the model can't reason over what wasn't retrieved/compressed into its window; (2) it reframes the "cognitive debt" thread (Aug 31) — the debt isn't only in unread code, it's in unmanaged context; (3) caveat — "context engineering" is a frame consolidating across the discourse, not yet a formalized role; instrument it via retrieval-precision and context-window-utilization metrics before treating it as a title.
