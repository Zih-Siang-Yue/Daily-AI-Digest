Core ML · Palettization Use Core ML Palettization for Native Weight Compression — Often More ANE-Friendly Than External int4

Thursday's tip covered MLX int4 quantization on the Mac before conversion, but Core ML has its own native compression path: ct.palettize replaces weight tensors with a 6-bit or 4-bit palette (lookup table), typically cutting a model 2–4x with minimal accuracy loss — and crucially, the Apple Neural Engine runs palettized ops natively, so you don't hit the "quantized op falls back to CPU" trap external quant can trigger. The deployable loop: convert your trained model with coremltools, then call ct.palettize with mode="kmeans" on the weight tensors, sanity-check on your eval set (cf. the Aug 22 eval gate), and ship the .mlpackage through Core AI. For a Binance iOS feature this is the in-pipeline compression step that pairs with Sep 1's MLX-LoRA→Core-AI path — tune with MLX, compress with palettization, deploy on Core AI. Instruments · Profiling Profile On-Device Inference With os-signposts in Instruments — Catch p99 Latency Regressions Before Users Feel Jank

Thursday's "verify ops land on the Neural Engine" tip answered where compute lands; this one answers how long it takes. Emit os_signpost intervals around each Core AI / Core ML inference call (begin/end around the predict), then open Instruments → "Points & Tracks" / the os-signpost instrument to see per-op latency, the GPU/ANE/CPU compute-unit breakdown, and thermal-throttling events on a single timeline. For a Binance iOS feature — an on-device transaction classifier or support triage — a regression in p99 inference latency shows up as a stretched signpost long before it surfaces as user-perceived jank in crash logs. The deployable practice: gate a release on a signpost-instrumented benchmark run in CI so a latency regression blocks the merge, not the App Store review. Signpost docs →

Background · Thermal Schedule Deferred On-Device ML Under BGTaskScheduler — and Gate on Thermal State So You Don't Cook the Device

Not every on-device ML job is latency-critical — a nightly personalization retrain, a deferred model update, a batch embedding refresh can run when the device is idle and charging. The pattern: schedule it under BGProcessingTask with requiresExternalPower: true and requiresNetworkConnectivity: false, and at run-time check ProcessInfo.processInfo.thermalState == .nominal before kicking off heavy inference/training — if the device is already .fair or .serious, defer to the next window rather than adding thermal load. For a Binance iOS feature this is the "when, not how" complement to the week's on-device tips: the heavy updatable-Core-ML personalization (Sep 1) or the int4 inference (Sep 3) shouldn't run during a trading session on a hot device — defer it. Pair with a .taskExpired handler that checkpoints progress so a pre-empted update resumes cleanly. BackgroundTasks →

Security · GitSpawn

"GitSpawn" — Malicious .git/config Can Hijack AI Coding Agents That Auto-Run Git Commands

A disclosed class of vulnerabilities, reported under the name "GitSpawn," exploits how AI coding agents (Claude Code, Codex, Cursor, plus Goose, Hermes Agent, Qwen Code) automatically run git status / git diff to gather project context: a malicious repository with a crafted .git/config can trick the agent into executing an attacker-specified command — deliverable via a ZIP, no clone required — running with the logged-in user's privileges (SSH keys, cloud creds, source code at risk). Claude Code fixed a core.fsmonitor issue (and the Sep 3 v2.1.260 release hardened git-config sandbox visibility on macOS, verified on the changelog); OpenAI published three CVEs for Codex (incl. CVE-2026-19592); Cursor and Goose (CVE-2026-72718) are patched; some agents remain unpatched. Why it matters: it's the concrete exploit of the "agent session as attack surface" thread (Aug 31) — the attack isn't the model, it's the context-gathering commands the agent runs on your behalf against untrusted repos. How to use it: update Claude Code/Codex/Cursor to the patched versions; never let an agent auto-run git against an untrusted repo without --restricted and a permission gate; and treat a cloned/extracted repo's .git/config as untrusted input. (The broader GitSpawn disclosure and CVE list are web-search-reported; the Claude Code v2.1.260 git-config fix is independently verified on the changelog. A concept surfacing as agent fleets grow (cf. today's GitSpawn vuln, which shows a single agent's context-gathering as an attack surface): alongside the per-agent harness (hooks, permissions, abort paths — "harness engineering," Sep 1), an org-level agent control plane is emerging — a governance layer that enforces policy across all agents in real time (an AI Gateway for tool/permission/data-access enforcement), manages artifact provenance (policy-compliant dependencies, the JFrog pattern), and coordinates multi-agent fleets. Why it matters NOW: (1) it's the layer above harness engineering — the harness bounds one agent; the control plane bounds the fleet, and today's GitSpawn vuln is exactly the failure a control plane catches (a single agent running git against an untrusted repo); (2) for a Binance platform team, the control plane is the procurement/governance boundary — standardize one (an AI Gateway with real-time policy) before allowing agent fleets into prod; (3) caveat — "agent control plane" is a frame consolidating across vendor announcements (Boomi Agent Control Plane, JFrog agent security — both web-search-reported this week, not yet primary-source-verified); instrument it via policy-coverage and blocked-action-rate before treating it as a productized category.
