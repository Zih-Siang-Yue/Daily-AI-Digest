💡 Daily Tech Tips — Monday: Claude Code / Codex (Agentic Workflow — Hooks, MCP, Skills)
Claude Code · MCP Fleet Push MCP Server Configs Fleet-Wide With managedMcpServers — Stop Hand-Configuring Every Dev's ~/.claude.json

Claude Code v2.1.259 (Sep 2, changelog-verified) added the managedMcpServers managed setting, letting an org push HTTP/SSE MCP-server configs to every Claude Code instance centrally instead of each developer hand-editing ~/.claude.json. Why it matters: it's the "agent control plane" (Sep 5 concept) made concrete for MCP — a new internal tool server (a Binance-internal data API, a deploy MCP) lands on every dev's agent via one settings file, not a ticket-per-machine, and the config is version-controllable and reviewable. How to use it: declare your team's MCP servers once in the managed settings file; pair with --permission-prompts none (today's tip 2) and an explicit permission allowlist so the auto-configured servers can't exceed their intended scope. Changelog →

Claude Code · Headless Run Claude Code Unattended With --permission-prompts none — For CI, Autoscaled Runners, and Scheduled Agents

v2.1.259 added --permission-prompts none for unattended headless hosts — Claude Code will not block on a permission prompt (and denies rather than hangs on an unplanned action). Why it matters: it's the primitive that lets an agent run inside CI / an autoscaled runner / a scheduled job without a human at a terminal to approve a tool call — the difference between "agent in a pipeline" and "agent that stalls the pipeline" (cf. the harness-engineering thread, Sep 1). How to use it: pair it with an explicit permission allowlist (allow only the read/safe-write paths the job needs) so the agent can do its bounded work and denies anything outside it; never run it interactively on a dev box where you want prompts. Changelog →

Claude Code · Subagents Load Large Subagent Personas From a File With --append-subagent-system-prompt-file — Bypass the Command-Line Length Limit

v2.1.261 (Sep 4, changelog-verified) added --append-subagent-system-prompt-file for prompts too large for the command line — point the flag at a file holding a subagent's system prompt and it's appended to the subagent's context. Why it matters: a real subagent persona (role, constraints, tool guidance, examples) easily exceeds shell argument limits; loading it from a file means you can version-control and review complex agent personas as code rather than cramming them into a one-liner — the "skills as reviewed artifacts" discipline. How to use it: keep your team's subagent personas in checked-in .md files, load them per-subagent, and run /skill-doctor (cf. Sep 6) to confirm the loaded persona is actually used and not silently bloating context. Changelog →

🔥 Hot Industry Concepts
Concept · Agent Protocols MCP vs ACP — The Two Complementary Agent Protocols (External Tools vs Internal Project Context)

A distinction consolidating across the 2026 architecture discourse: the Model Context Protocol (MCP), Anthropic's late-2024 "USB-C for AI," connects an agent to external tools / data / services; the Agent Context Protocol (ACP) operates a level up — a structured system that gives an agent internal understanding of the project it works on (architectural decisions, milestones, coding patterns). In short: MCP connects an agent to its external tools, ACP gives it the internal "beliefs and goals" to reason about the project. Why it matters NOW: (1) for a Binance team, MCP is the integration layer (today's managedMcpServers tip) and ACP is the project-context layer — instrument both and don't conflate them; an agent with MCP but no ACP can call your tools but doesn't know your codebase's intent. (2) It refines "context engineering" (Sep 3, 4): part of context engineering is which protocol carries what — MCP carries tool-results, ACP carries project-beliefs. (3) Caveat — "ACP" as a named standard is still consolidating across the discourse; instrument it via tool-invocation-coverage and project-context-recall before treating it as a productized protocol.
