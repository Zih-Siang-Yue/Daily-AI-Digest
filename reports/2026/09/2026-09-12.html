MLX · Decision Matrix Pick MLX Swift for Dynamic-Prompt On-Device LLMs, Core ML for ANE-Optimized Static Models

The "which on-device runtime" question has a clean answer: reach for MLX Swift when your workload needs dynamic prompt lengths, native .safetensors loading (no coremltools conversion pass), and KV-caching — it runs eager-on-Metal across unified memory, ideal for open-weight SLMs (Qwen, LLaMA, Gemma) where prompt shapes vary per turn. Reach for Core ML when the model is static, runs frequently or in the background, or must hit the Neural Engine for best tokens-per-watt — its ahead-of-time graph compiles to ANE-optimized INT8 that won't thermal-throttle a passive-cooled iPhone. Why it matters: MLX trades battery and heat for flexibility; Core ML trades flexibility for efficiency — match the runtime to whether your user holds a long conversation (MLX) or runs a recurring background task (Core ML), and you avoid the two classic on-device failures (a flexible MLX model that throttles, or a rigid Core ML graph that breaks on variable prompts). Model Delivery · Background Assets Ship a Multi-GB On-Device LLM Without Bundle Bloat — Background Assets Downloads + mmap'd Weights

Embedding a multi-gigabyte on-device LLM inside your app bundle blows past App Store size limits and wastes device storage for users who never open the feature. The pattern: declare the model as an on-demand Background Assets download (iOS 16.3+) so iOS fetches and patches weight files in the background, then load the .mlpackage / .safetensors file with mmap so only the memory pages you touch resident in RAM — keeping peak memory low and first-launch fast. Why it matters: for a Binance feature that's optional (an in-app support LLM, on-device transaction summarization), background download + mmap is the difference between a 3 GB bundle and a 50 MB one, and it lets you ship model updates without an app release — the same patching model the OS uses for system assets. Background Assets →

Foundation Models · On-Device Agents Foundation Models Framework Tool-Calling — Build a Private On-Device Agent on the System SLM (Beyond Guided JSON)

Apple's Foundation Models framework (iOS 26) exposes the on-device system SLM (~3B) not just for guided JSON output (covered Sep 4) but for tool-calling — you declare function schemas and the model emits tool calls your app executes locally, giving you a private, zero-cloud agent loop for in-app actions. Why it matters: for a Binance iOS feature (natural-language trade-status lookup, on-device transaction categorization), an on-device tool-calling agent keeps user data on the phone, removes per-call inference cost, and — because it's the system model — requires no multi-GB download (cf. today's Background Assets tip is for the models you ship yourself). How to use it: define your app's actions as Foundation Models tools, gate each behind your existing permission layer, and keep a deterministic fallback path for high-stakes operations so the agent never books a trade it can't unwind. 🔥 Hot Industry Concepts
Architecture · Mobile Local-First Architecture & CRDT Sync Engines — The Offline-First Pattern Maturing for Mobile

The local-first architecture paradigm — where a client-side embedded database (SQLite via GRDB/SQLDelight, IndexedDB) is the source of truth for UI state and CRDT-based sync engines (PowerSync, ElectricSQL, Zero) stream changes bidirectionally to the cloud — has matured into a mainstream mobile/web pattern: the app reads and writes a local DB synchronously and syncs in the background, so the UI never blocks on a network round-trip and works on a dead connection. Why it matters NOW: for an iOS dev, local-first is the answer to zero-latency UI and reliable offline support — and it's the architectural counterpart to on-device AI: the model is local, so the data should be too. An on-device LLM querying a local CRDT-synced store (today's Foundation Models tip + this pattern) is the privacy-first, offline-capable agent stack. Caveat: pick a sync engine whose conflict-resolution semantics match your data (last-write-wins vs. CRDT merge) — the hard part is the sync, not the local DB. Local-First →
