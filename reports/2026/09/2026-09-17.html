💡 Daily Tech Tips
Core ML · Edge AI Ship an On-Device LLM on the Neural Engine With Core ML Stateful Models + MLTensor

Core ML's stateful-model API lets you embed an explicit KV-cache as state directly inside the compute graph, so a sub-3B SLM executes on the Apple Neural Engine (best tokens-per-watt, no thermal throttle) rather than falling back to the GPU the way an MLX eager loop does. Why it matters: it closes the gap that made MLX Swift the default for on-device generative LLMs — you keep graph-level ANE scheduling and battery efficiency and get stateful multi-turn generation, which is the shape a private in-app support or transaction-summarization LLM needs. How to use it: convert your PyTorch model with coremltools.convert(..., stateful=True), expose the KV-cache as an MLTensor state dict, and benchmark tokens/sec against the MLX Swift baseline on the same physical device before committing — ANE wins on sustained background inference, MLX wins on dynamic prompt shapes. coremltools →

Hybrid Pipeline Run Core ML Perception on the ANE + an MLX Swift LLM on the GPU Concurrently — They Don't Contend

The cleanest production on-device agent stack is a hybrid: a Core ML vision/audio model on the Neural Engine feeds structured context into an MLX Swift generative LLM running on the Metal GPU — and because the ANE and GPU are separate execution units on Apple silicon, they run concurrently with minimal hardware contention. Why it matters: it ends the false "Core ML or MLX" choice (cf. Sep 12 decision matrix); the real answer for a full agent (perceive → reason → act) is both, each on the unit it wins on, which is the shape your iOS on-device agent will take once you go past a single model. How to use it: run the Core ML perception pass on a .neuralEngine compute-unit preference, hand its typed output to an MLX Swift generation loop on .gpu, and verify with Instruments that the two never serialize on the same unit. Benchmarking Don't Trust the Simulator for On-Device ML — Build a Physical-iPhone tokens/sec & Peak-RSS Harness

Metal compute behavior is not fully emulated in the iOS Simulator, so a model that "feels fast" in Xcode can thermal-throttle or balloon memory on a real iPhone — the only trustworthy numbers come from a physical-device harness that logs tokens/sec, time-to-first-token, and peak resident memory under sustained load. Why it matters: the difference between "shippable" and "throttles after 30 seconds" is invisible until you measure on silicon, and it's the gate that decides whether your on-device LLM survives a real support-chat session or collapses on the second user turn. How to use it: wrap your generation loop in an os_signpost interval (cf. Sep profiling tip), sample mach_task_basic_info for RSS, and run a 50-turn conversation on the oldest supported device — gate the merge on a tokens/sec floor and a "no throttle for 5 min" ceiling, not just correctness. Trending "Spec-Driven Agentic Engineering" — Vibe Coding Grows Up
