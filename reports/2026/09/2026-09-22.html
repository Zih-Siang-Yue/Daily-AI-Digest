💡 Daily Tech Tips — AI x iOS (Core ML · Create ML · MLX On-Device)
MLX · Speculative Decoding Run Speculative Decoding On-Device — ANE Draft (Core ML) + GPU Verify (MLX Swift) for ~1.5–2× tok/s

The highest-leverage on-device-LLM speedup is also the least-used on iOS: a tiny quantized draft model runs on the Apple Neural Engine via Core ML proposing tokens, while the main model verifies them on the GPU via MLX Swift — gaining 1.5–2× tokens/sec with zero quality loss, because the ANE excels at the compute-dense draft-proposal step and the GPU handles the memory-bandwidth-bound verify. Why it matters: it’s the concrete use of the hybrid ANE+MLX split (carded Sep 17 as a topology) pushed into an actual inference optimization, and it’s the pattern that makes a 3B-SLM chat feel instant. How to use it: enable the draft path in mlx-lm (prompt-lookup or a small matched draft model), let Core ML compile the draft to the ANE, and pass proposals through a shared IOSurface buffer so there’s no copy — benchmark with the physical-iPhone harness from Sep 17, never the simulator. Apple Intelligence Default to the System Foundation Models API Before Bundling a 4-bit SLM — Zero App-Download Footprint

Before you ship a bundled .mlpackage or MLX weights file, check Apple’s Foundation Models framework (System Foundation Models API): it exposes the on-device ~3B Apple Intelligence model (summarization, proofreading, entity extraction, tool-calling) with no model download, no added app size, OS-managed context, and ANE-optimized thermals — the system model is the zero-cost default. Why it matters: for an iOS feature that needs summarization/extraction, the system model is the right first choice; you only fall back to a bundled MLX weights file when you need a model the system one can’t run (custom open-weights LLM, fine-tuned behavior) — and that decision directly shapes your app-size and battery budget. How to use it: guard on Apple-Intelligence availability, call the system model first, and reserve mlx-lm 4-bit conversion for the features the system model can’t cover. Apple ML →

Memory · Jetsam Budget the KV-Cache Against Jetsam — Poll os_proc_available_memory() and Shed Before iOS Kills Your App

The #1 cause of on-device-LLM crashes isn’t the model weights — it’s the unbounded KV-cache growing under long context: a 4-bit 3B SLM needs ~1.6–2 GB of weights, and iOS terminates foreground apps past ~3.5–5 GB on a 6–8 GB device, so a long conversation’s KV-cache is what pushes you over. Why it matters: it’s the memory analog of the thermalState gate (Sep 15) — you must shed load before the Jetsam killer fires, not after — and it directly determines your usable max context length. How to use it: cap max_tokens/context, evict oldest KV pages on a rolling basis, and poll os_proc_available_memory() each turn to degrade gracefully (truncate history) before the OS acts.
